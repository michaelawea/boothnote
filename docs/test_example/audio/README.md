# 测试音频 —— 转写效果的基准

> issue #15（维护者 2026-08-05）：「其语音也可以作为判断 stt 效果的一个点」。

## 为什么需要这个目录

转写改动是**最容易自我欺骗**的一类改动：加几个关键词进 prompt，
新词对了，然后你就以为改好了 —— 而原来对的那些可能已经被带坏了。

规划文档 §2 记过一条实测：品牌名 prompt 偏置在 12 / 20 / 30 / 56 个品牌下
**非单调**。也就是说「加词表」不是单向变好的操作，它是在一条噪声曲线上移动。
**没有基准音频，就没有办法知道自己往哪边移动了。**

## 怎么放

一段音频 + 一份同名的 `.expect.json`：

```text
audio/
├── README.md
├── T07_CI-Bus_新项目.m4a           ← 真人录的，手机上录的最好（那才是现场的信道）
└── T07_CI-Bus_新项目.expect.json   ← 这段话里必须被听对的词
```

`.expect.json` 的形状：

```json
{
  "note": "T07 的口述原文。最容易听错、而且听错了后果最重的是型号和协议名。",
  "must": ["CI-Bus", "VLB12150-CIBUS", "Havel", "ECWVTA", "SOP"],
  "nice": ["欧洲 OE", "整车验证", "20 台"],
  "mustNot": ["sea bus", "CBUS", "Highmer"]
}
```

- `must` —— **听错了就是错误归属/错误产品**，一条不中就算失败；
- `nice` —— 影响信息完整度，不中只扣分；
- `mustNot` —— 已知的错法。出现任何一个立刻标红，这是回归的早期信号。

匹配是**大小写不敏感 + 忽略空格和连字符**的（`CI-Bus` / `CI Bus` / `cibus` 都算中），
因为下游的抽取那一步本来就会做归一化 —— 我们要的是「听出了这个东西」，
不是「一个字符不差」。

## 怎么跑

```bash
node scripts/stt-eval.mjs                    # 全部
node scripts/stt-eval.mjs T07                # 只跑名字里带 T07 的
node scripts/stt-eval.mjs --no-terms         # 不喂词表，看基线（对照组）
```

它会真的调一次转写接口（**要花钱**，一段 60 秒的音频很便宜），
并且把两种配置的结果并排打出来，让「词表到底有没有用」这件事**可测**
而不是靠感觉。

## 🔴 改完转写必须跑一次

`services/gateway/agent/src/transcribe.ts` 或 `data/stt-terms.json` 一动，
就在这里跑一遍再提交。判据：

- `must` 全中 → 可以提交
- 任何 `mustNot` 命中 → **不要提交**，那是明确的回归
- `nice` 掉了几个 → 记进 PR 描述，让下一个人知道代价

## 录音怎么录

- **用真手机、在真 https 页面上录**（PWA 那条路），不要用电脑麦克风导出 wav：
  容器格式、码率、降噪都不一样，而那正是我们要测的信道（T8 那条风险）；
- 语速正常，别刻意咬字 —— 展会现场是边走边说的；
- 如果有德语/英语混着说的样本，**那是最有价值的一条**（缺口 #4：现场德/英/意混杂）。

音频文件不进 git（见 `.gitignore`）—— 它们可能包含真实客户信息，
而且二进制文件会把仓库撑大。放在服务器/本地即可，`.expect.json` 进 git。
