## 1. 问题摘要

Havel 在样品测试中可以观察到 CI-Bus/CAN 总线流量，但当前工具未能解析 SOC 和告警状态。现有证据不足以判断是接线、协议、软件配置还是样品本身的问题。

## 3. 工作线程

### 3.1 文档线程

目标：提供通信端口说明，包括端口位置、连接器、安装和使用限制。

待确认：文档语言、格式以及客户是否有指定模板。

### 3.2 硬件接口线程

目标：提供 Pin 脚与电气特性，确认 CAN-H、CAN-L、GND、屏蔽和终端电阻。

待确认：连接器型号、线束版本、总线拓扑、终端电阻实测值和电压电平。

### 3.3 通信协议线程

目标：说明 `0x351`、`0x355` 的方向、周期、字段、字节序、缩放和异常处理。

待确认：协议版本、固件版本、节点地址、握手流程及客户需要解析的完整信号列表。

### 3.4 测试软件线程

目标：提供适用于 Ubuntu 24.04、Python 3.12 和 SocketCAN `can0` 的最小测试程序。

待确认：USB-CAN 型号、依赖安装权限、期望输出格式和客户当前代码版本。

## 4. 任务依赖

- 测试软件依赖最终 Pin 定义和协议字段定义；
- 通信端口文档应引用确认后的硬件接口版本；
- 四条线程的结论应汇总到同一项目跟进记录中。

## 5. 计划与期限

- 客户原始要求：三个工作日内收到初步回复；
- 明确截止日期：由系统基于记录创建时间及工作日日历计算；
- 若系统没有节假日日历，应标记计算口径并请求人工确认。

## 6. 建议关键追问

客户当前使用的连接器/线束版本是什么，CAN 总线两端的终端电阻配置和实测阻值分别是多少？

## 7. 信息边界

- “能看到报文”不等于协议解析正确；
- “未显示 SOC”不等于电池没有发送 SOC；
- 在获得完整日志、线束信息和协议版本前，不应下结论为产品故障；
- 后续客户确认或补充文档后，应创建新版本并保留本记录。
