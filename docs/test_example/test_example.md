# CRM Agent 真实业务场景测试用例

> 版本：v1.0  
> 测试客户：Havel（虚构测试数据）  
> 适用范围：数据库模型设计、Agent 信息抽取、文档处理、业务流程联调  
> 说明：本用例描述的是实际工作中希望系统具备的能力，不受当前数据模型或 Agent 能力限制。

## 1. 使用说明

### 1.1 测试目标

这组用例用于验证系统能否把销售人员的自然语言、口述参数和客户文档，转换为可持续跟进的 CRM 数据。测试结果也应反向推动：

- 数据对象、字段和对象关系的补充；
- Agent 的意图识别、信息抽取和追问策略优化；
- 附件解析、文档创建、版本管理和关联能力完善；
- 商机、项目、技术问题和任务之间的业务流程补全。

### 1.2 执行约定

1. 用例应按 `T01 → T07` 的顺序执行，以验证上下文延续能力；也可以在清空测试数据后单独执行。
2. 所有名称、金额、日期、编号和技术参数均为测试数据，不代表 Havel 或任何实际公司的真实信息。
3. “系统应创建”的内容可以先进入待确认区，但确认后必须能形成正式记录。
4. 对无法从输入中确定的信息，Agent 应明确标记“待确认”，不能静默猜测。
5. Agent 可以计算派生值，但必须保留原始表述，并标注计算依据。
6. 同一段输入重复提交时，不应生成重复客户、重复商机、重复项目或重复问题。
7. 本目录中的 `expected_outputs/` 文件仅用于描述期望结果；执行“无文档”测试时，不得作为输入附件上传。

### 1.3 通用验收维度

| 维度 | 验收要求 |
|---|---|
| 信息完整性 | 客户、业务对象、产品、数量、金额、阶段、时间、负责人和来源信息应尽量完整 |
| 原文保真 | 保留用户原话或原始附件，结构化结果能够追溯到来源 |
| 对象识别 | 正确区分客户、商机、项目、需求、技术问题、任务和文档 |
| 关系正确 | 新记录应关联到正确客户和上游业务对象，不产生孤立数据 |
| 不确定性 | 缺失、冲突和推断信息必须有明确标记，必要时提出少量关键追问 |
| 文档能力 | 能解析输入文档，也能在无附件时根据口述内容生成结构化文档 |
| 可管理性 | 记录可搜索、筛选、更新、分派、查看状态和跟踪历史版本 |
| 幂等与去重 | 重复输入不会产生重复对象；相似对象出现时应提示合并或关联 |

## T01：新建商机——竞争信息与需求量录入

### 测试目的

验证 Agent 能否从一段销售口述中识别客户、竞争品牌、产品组合、价格接受度、年需求量和关键时间，并创建一条信息完整的商机记录。

### 前置条件

- CRM 中已存在客户 `Havel`；
- 当前不存在名称为 `Havel 12V 锂电池年度供应商导入` 的未关闭商机；
- 本用例无附件。

### 用户输入

> 刚和 Havel 的项目团队开完会。他们正在为 2027 款房车寻找 12V 锂电池供应商，预计年需求量 20,000 台。现在主要使用 Voltaro，单台可接受价格大约 500 欧元。产品组合是 100Ah 和 150Ah，其中 100Ah 约占 30%，150Ah 约占 70%。希望 2026 年 10 月底前确定候选供应商，先把这个机会建起来。项目由欧洲 OE 销售团队负责，初步预计首年采购预算为 900 万欧元。

### 输入附件

无。

### 期望业务动作

1. 识别 `Havel` 为客户，不把 `Voltaro` 误识别成客户。
2. 新建商机，并关联到 `Havel`。
3. 将两种容量和占比作为产品需求明细保存，不能只保留其中一种型号。
4. 将竞品、价格接受度、年需求量、预算和决策窗口保存为可检索信息。
5. 根据 20,000 台与 30%/70% 计算参考数量时，标记为派生值：100Ah 约 6,000 台、150Ah 约 14,000 台。
6. 如果系统无法承载“价格接受度”或“产品组合占比”，应新增合适的字段或明细对象，而不是把信息丢弃。

### 期望核心数据

| 字段/对象 | 期望值 |
|---|---|
| 客户 | Havel |
| 商机名称 | Havel 12V 锂电池年度供应商导入 |
| 商机简介 | Havel 为 2027 款房车寻找 12V 锂电池供应商 |
| 业务阶段 | 已接触 / 需求确认中 |
| 产品品类 | 12V 锂电池 |
| 年需求量 | 20,000 台/年 |
| 100Ah 需求 | 30%，参考数量约 6,000 台/年（派生值） |

| 当前竞品 | Voltaro |

| 首年采购预算 | EUR 9,000,000 |
| 决策窗口 | 2026-10-31 前确定候选供应商 |
| 负责人 | 欧洲 OE 销售团队 |
| 信息来源 | 销售口述 / 客户会议 |

### 验收断言

- [ ] 商机只创建一次，并正确关联 Havel。
- [ ] Voltaro 被记录为竞品或当前供应商，而不是客户。
- [ ] 20,000 台总量、30%/70% 占比和两种容量均未丢失。
- [ ] 6,000/14,000 台被标记为系统计算值，不冒充客户原话。
- [ ] “约 500 欧元”被记录为价格接受度，而不是已经确认的成交价。
- [ ] 商机名称、阶段、预算、决策窗口和负责人均可在 CRM 中展示与筛选。

## T04：项目跟进——有技术需求文档，拆分多线程问题

## T05：项目跟进——无文档，生成技术需求记录

## T07：全新项目识别——口述、无附件、客户可能不在名单里

> 🔴 **这一条是 2026-08-05 手机实测直接产生的**（issue #17）。
> 维护者 用一个真实的 CI-Bus 新项目走了一遍，结论是「完全没有按照我的预期」：
> 它被记成了**选型情报**，而不是项目。事后查出来这不是模型能力问题 ——
> `list_enums` 里根本没有 `project` 这个值（V1/V2 两份枚举各走各的），
> 它**没地方表达「这是项目」**。
>
> 所以这条用例守的是一件很具体的事：**「这是一个新项目」这个判断本身**。
> T02 测的是「从已有商机建项目」，前提是客户和商机都在；
> 这一条测的是最难的那个入口：**什么都还没有的时候，它认不认得出来。**

### 测试目的

验证 Agent 在**只有一段口述、没有附件、客户不一定对得上号**时能否：

1. 判断出这是一个**全新项目**，而不是对已有项目的更新，也不是一条选型情报；
2. 不确定时**主动问一句**（而不是猜一个，也不是沉默地按默认处理）；
3. 把口述里的时间线**结构化成可跟踪的线程**，而不是塞进一段详情文字；
4. 编号缺失时不自己编，把这一步留给人/网关。

### 前置条件

- CRM 中已存在客户 `Havel`（若测「客户对不上号」的分支，改用一个不在名单里的名字）；
- **不存在**任何编号以 `EHG-HAVEL-` 开头的当年项目（否则测的是更新不是新建）；
- 本用例无附件。

### 用户输入

> 刚跟 Havel 那边开完会，CI-Bus 这个事定下来了，他们决定用我们的方案，
> 要正式立一个项目。核心产品是 VLB12150-CIBUS，先做 20 台样品。
> 时间上：八月中我们把通信协议说明发过去，九月他们装车做整车验证，
> 十一月底前要完成 ECWVTA 相关的测试，明年三月 SOP。
> 项目这边我们出欧洲 OE 项目团队。连接器型号他们还没定，等他们给。

### 输入附件

无。**不得**上传 `attachments/` 或 `expected_outputs/` 里的任何文件。

### 期望业务动作

1. `recordType` 判为 **`project`**（不是 `fitment`，不是 `followup`）；
2. 先查一次「这个项目是不是已经存在」——客户对得上号就按客户查，
   对不上号就按项目名/编号模糊查；
3. 调用 `propose_project` 提交项目提案（名称、核心产品、样品数量、
   计划 SOP、负责团队、待确认事项）；
4. 调用 `propose_work_items` 把口述里的时间线拆成**至少 4 条**线程：
   - 通信协议说明（`protocol`，8 月中）
   - 整车验证装车（`milestone`，9 月）
   - ECWVTA 测试（`milestone`，11 月底前）
   - SOP（`milestone`，次年 3 月）
5. `propose_fields` 照常提交 `summary` / `details`（两个工具都要调，不是二选一）。

### 期望核心数据

| 字段 | 期望值 |
|---|---|
| recordType | `project` |
| project.name | 含「CI-Bus」 |
| project.projectCode | **留空**（原话没给编号），由人/网关补 |
| project.primaryProductName | `VLB12150-CIBUS` |
| project.sampleQty | `20` |
| project.plannedSop | 次年 `03` 月的一个日期 |
| project.ownerTeam | 含「欧洲 OE」 |
| project.openQuestions | 含「连接器型号」 |
| workItems | ≥ 4 条，每条有 `dueDate` |
| sourceConfidence | `CONFIRMED`（「我刚跟他们开完会」= 本人在场） |

### 验收断言

- [ ] 🔴 `recordType` 是 `project` —— **不是 `fitment`**（issue #17 的原始症状）。
- [ ] 🔴 提交了项目提案（`extracted.project` 非空）。只交字段不交项目的，这一条判失败。
- [ ] 🔴 口述里的四个时间点**在 CRM 里是四条可跟踪的线程**，不是 `details` 里的四行文字。
- [ ] Agent 没有自己编项目编号；核对卡上出现一个**网关生成的建议编号**，人可以改。
- [ ] 「连接器型号还没定」进了待确认，**没有**被补成一个看起来合理的型号。
- [ ] 相对期限（「八月中」「十一月底前」「明年三月」）被转成了具体日期，同时保留原话。
- [ ] 客户对不上号的那个分支里：`companyCode` 留空，`flag_new_company` 提议，
      **其余字段照常提交**（不是一个字段都不交）。
- [ ] 确认入库之后，CRM 里**真的出现了这个项目** —— 而不是界面显示「已入库」但项目不存在。

### 语音版本（STT 评测点）

这一条同时是**转写效果的基准**（issue #15）。把上面那段话录成音频放在
`audio/T07_CI-Bus_新项目.m4a`，然后：

```bash
node scripts/stt-eval.mjs
```

它按 `audio/*.expect.json` 里的关键词逐条打分。这段话里最容易被听错、
而且**听错了后果最重**的是这几个：`CI-Bus`（会变成 "sea bus"/"CBUS"）、
`VLB12150-CIBUS`、`ECWVTA`、`Havel`、`SOP`。
品牌名和型号听错 = 归属和产品认错，是这条链路上最贵的错误。
