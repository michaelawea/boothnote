# 售后问题（support）

判据：**已经交付的东西出了毛病**，需要闭环解决。
信号词：售后、报修、故障、不工作、投诉、退货、保修、现场排查、工单。
**只要句子里出现「售后」两个字，就是 support。**

## 状态与严重度

顺带给 `caseStatus` 和 `severity`：能修好的写 RESOLVED，还没动的写 NEW。
合法值用 `list_enums` 查，别背。

- `deliveryBatch` 交付批次：**原话照抄**（「2025-03 批次」「MY2025 首批」），别换算成日期。
- `affectedUnits` 影响台数：**只有原话明确说了数字才填**。
  「好几台」「一批」一律留空 —— 猜一个数字比留空糟得多，
  它会被拿去排「哪个问题影响面最大」。

## 是新问题还是老问题的进展？

客户对上号之后 `get_company_records` 查已有售后，比较正文里的故障、SKU、车辆与历史排查，
**同客户、同SKU或最近的一条不等于同一问题**。不同故障要用 `propose_records` 拆成独立事项。

推荐目标但用户没明确指定编号时，用 `ask_user` 的 `targetOptions` 引用返回的 `candidateHandle`，
推荐项用 `recommendedIndex` 标明，并给「新问题」（create）和「都不是/补充说明」（clarify）出口。
问「这次排查回复要追加到 <标题> 并置为 WAITING_CUSTOMER 吗？」——
不要只说「待人工关联」再让销售自己翻完整列表。多事项时传该项 `itemId`。

原话明确指定编号/UUID且校验客户一致时，可用当前已注册提案工具的 `targetCandidateHandle` 预填，
不机械重复问。检索失败/未读完与零候选分开，失败保留提案，不自动新建。
已关闭/已解决的工单显示真实状态，不静默追加或重开。
选项确认只绑定待核对提案，真正写CRM仍须人工确认入库。

## 详情结构（写进 `details`，markdown）

售后类按这个结构写，没有的段就省掉，**别编**：

```
## 车辆与合同     车型、合同号、是不是首批装机
## 涉及的产品     具体型号，一个一行
## 客户链         终端 → dealer → 整车厂 → 我们
## 现象           客户报的每一条，逐条列
## 根因           编号列，每条写清依据；**没定论的要写「未定论」**，不要含糊过去
## 已做 / 待做    时间 + 做了什么 / 谁负责什么
## 结论
```

带附件（技术报告、现场照片）时，附件里的细节**逐条转录进 details**（详见 attachment 手册）：
车辆型号、合同号、涉及的 SKU、客户链、时间线、每一条根因、待办 —— 宁可长，不要漏。
