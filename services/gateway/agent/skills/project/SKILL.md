# 项目与跟进（D59 那条链）

**成交之前的一切是「商机」，定点之后的一切是「项目」。**
商机回答「这单能不能做成」，项目回答「做成之后怎么交付」。这两个不要混。

## 项目提案必须包含项目与交付事项

旧单项路径必须调一次 `propose_project`：`propose_fields` 记「这条讲了什么」，项目工具记「CRM要长出哪个项目」，两个都要。
多事项路径用 `propose_records`，该项的 fields 带完整 project/workItems/docs，不能再压回一个 `propose_fields`。
只交摘要的话，人在核对卡上看到一堆字段，
而 CRM 里没有任何项目 —— 那正是这个功能存在的全部意义。

判据（命中任一就是 project）：原话里出现
「定了我们 / 已经定点 / 新项目 / 建个项目 / 立项 / 基于之前的商机建项目 / 项目编号」。

## 新项目还是已有项目？—— 必须查，不能猜

**先 `get_projects` 看编号在不在**：在就是更新（传同一个 projectCode），不在才是新建。

对未明确指定编号的跟进，先查候选差异，再用 `ask_user(targetOptions,recommendedIndex)`
给推荐项目/任务及 create/clarify 出口，候选句柄来自读工具，不自行编 UUID。
原话已明确指定经过校验的编号时预填，不要求用户重选。
API故障/分页未完整读取不能当成「没有项目」；自己的待确认候选与CRM已入库对象明确区别。
多事项的问题指定 itemId，答案只推进那个事项，不复制或取代同thread其它事项。

🔴 **原话明说「立一个项目 / 新建项目 / 建个项目」= 新项目，编号留空** ——
哪怕这家名下已经有名字相近的项目也一样。**不要把已有项目的编号拿来复用**：
「立项」和「更新」是两个动作，你合并了它们，人就再也分不开了。
名下确实有相近的项目时，在**回话里**提一句「这家已有 <编号> <名字>，
如果说的其实是同一个，人在核对卡上把编号改过去就行」—— 决定留给人。
复用已有编号只有两种情况：原话明确说「更新 / 推进 <编号>」，
或内容明显是**同一个项目**的后续跟进（阶段推进、样品反馈这类）。

🔴 **客户还没对上号也照样调 `get_projects`** —— 这时候填 `query`
（项目名或编号的一部分，如「CI-Bus」「HYM-BAT」），它会全库找。
猜错的代价：新项目被记成对已有项目的修改，或者反过来多出一个重复项目。
两条路都查不出来时，用 `ask_user` 问一句 —— 这个问题值得占掉那一次提问机会。

编号规则：原话给了就**逐字照抄**（HYM-BAT-2027-001 这种，连大小写都不改），
没给就**留空** —— **不要自己编一个编号**：编号是幂等的支点，
你编的下次认不出是同一个项目。

🔴 **留空之后网关会当场给一个真编号**（D91，2026-08-07 起），
就写在这个工具回给你的那句话里（「已记下项目提案「…」（编号 HMG-HAVEL-2026-001）」）。
所以**写小结时直接用它**，不要再说「编号待定」——
这个编号从此就是这个项目的身份，人在看板上按它把同一个项目的多条对话并成一张卡。
回话里如果说「这家客户这个品类已经有一条提案在用它」，意思是**接到了同一个项目上**，
那不是错误，是对的：同一家客户 + 同一个品类 = 同一个项目（D56）。
只有客户还没对上号时才拿不到编号（前缀就是客户代号）——
那时候人在核对卡上选完客户会看到一个建议编号。

🔴 **`get_projects` 全库查出来的项目，先看它属于哪家客户**（每条都标了）。
名字相近但属于**别家客户**的项目不是同一个项目 —— 绝不要复用它的编号。
这条速记的客户名下没有匹配时，就是新项目，编号留空。

## 跟进（followup）

听到「更新 <项目编号>」+ 一堆要做的事 → 这是一次**跟进**。

🔴 **如果原话里项目阶段变了，跟进时也要调一次 `propose_project`** ——
传同一个 projectCode + 新的 projectStage（同编号 = 更新，不会新建第二条）。
「已经进入样品测试阶段」「开始整车验证了」这类就是阶段变化。
实测漏过一次（2026-08-03 T04）：只提了线程没提项目，四条线程建对了，
**而项目阶段还停在「定点」** —— 看板上那个项目看起来根本没动。

## 拆任务线程（`propose_work_items`）

判断该不该拆的标准：**这几件事会不会由不同的人在不同的时间做完？**
「要端口说明 + Pin 定义 + 协议说明 + 能跑的测试代码」= 四条线（文档/硬件/协议/软件），
负责角色和截止日期都不一样 —— 合成一条就没法分派，也看不出谁卡住谁。
**一次全部提交**（工具收数组），不要一条一条调。

## 🔴 时间线：每一个带日期或期限的事项，都要拆成一条线程

纯时间点（「9 月装车」「Q4 定点」「明年三月 SOP」）用 `threadType=milestone`，
要做的事按类型（doc/hardware/protocol/software）。**一行一条，`dueDate` 必填**。
同时在 `details` 里保留原话 —— 两边都要。
**只写进 `details` 的时间线，在 CRM 里排不了期、提醒不了、也看不出谁卡住谁**：
它只是一段好看的文字，而这套系统要的是能跟踪的记录。
附件里的**里程碑表**同样用它（一行一条，带目标日期）。

**相对期限要转成日期，同时保留原话**：「三个工作日内回复」→
`customerDueDate` 填算出来的日期，`body` 里写「客户原话：三个工作日内」。
只留一个都不行 —— 只有日期就丢了语气，只有原话就排不了期。

## 文档（`propose_document`）

客户**没给文档**但说了一堆参数 → 整理成一份。
🔴 `docSource` 如实填：你整理的是 `DICTATION`，客户给的附件是 `CUSTOMER_ATTACHMENT`。
口述整理的正文开头写明「根据口述整理，未经客户书面确认」，
**没提到的参数单列一段「待客户确认」—— 绝不要补成已确认值**。
客户给了正式规格书 → 也用它登记（`CUSTOMER_ATTACHMENT` + `isBaseline: true`）。

## 🔴 不确定的东西一律进 `openQuestions`，不要编进正文

「连接器型号未提供」「终端电阻配置未知」这种，写进待确认。
编一个看起来合理的参数进去，三个月后没有人分得清它是客户说的还是你猜的。
